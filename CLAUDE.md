## Project

Backend for the Backslash Security home assignment: a graph analysis platform. Users upload JSON files (multipart) describing a microservice architecture as a directed graph (nodes, edges, vulnerabilities); the API stores them in PostgreSQL, keeps an in-memory graph for traversal, and answers route queries with dynamic filters. Backend only; a React frontend lives in the sibling `home-exercise-backslash-fe` folder. Stack: Node, TypeScript, Express 5, Prisma 7, PostgreSQL, Zod 4, pino, Jest + Supertest, Docker Compose.

## Architecture

Request flow: `router -> controller -> service -> repository (interface) <- prisma-* implementation`. Controllers only translate HTTP; services hold business logic and depend on repository interfaces (and a planned `TransactionRunner`), never on Prisma directly, so they unit-test with in-memory fakes.

- `src/container.ts` is the composition root (manual DI, no library). `wireApp()` builds services/controllers from given repositories and is what tests call with fakes (`tests/helpers/test-app.ts`); `createContainer()` builds the real Prisma-backed infrastructure.
- `src/app.ts` builds the Express app without listening (Supertest-friendly). API is mounted under `/api/v1`; `/health` and `/docs` sit outside it. Order matters: request-id -> request logger -> cors -> json -> routers -> not-found -> error handler.
- Errors: throw `AppError` subclasses (`src/http/errors.ts`); `error-handler.ts` maps them, `ZodError` and body-parser errors to the shared `{ error: { code, message, details? } }` format. Never leak stack traces on 500.
- OpenAPI is generated from Zod schemas (`@asteasolutions/zod-to-openapi`, 3.1). Each module exports a `register*Docs(registry)` function called from `wireApp()`. `extendZodWithOpenApi(z)` is called once in `src/http/openapi/registry.ts`.
- Validation middleware (`validate.ts`) redefines `req.query` via `Object.defineProperty` because it is a getter in Express 5.
- Prisma client is generated to `src/generated/prisma` (gitignored; regenerated by `npm install` and `npm run build`) and uses the `@prisma/adapter-pg` driver adapter. `prisma.config.ts` loads `.env` itself because Prisma 7 does not.

### Data layer (Task 2, implemented)

- Repositories: `GraphRepository` / `FilterRepository` interfaces with `Prisma*` implementations that take a `DbClient` (root client or transaction client). Write flows use `UnitOfWork` (`src/modules/unit-of-work.ts`): `unitOfWork.run(({ graphs, filters }) => ...)` gives repositories bound to one transaction. Services (Task 3+) must call `graphs.bumpVersion(id, ifMatch?)` **first** in every write transaction (it is the row lock and the optimistic-lock check), then write, then drop the cache after commit.
- `findWithData` reads graph + nodes + edges in a REPEATABLE READ transaction for a consistent snapshot. Edges come back sorted by (from, to); nodes by `position`.
- `src/infrastructure/prisma.ts` understands `?schema=` in `DATABASE_URL` (sets both the adapter `schema` and `search_path`, so raw SQL and generated queries agree).
- Error mapping lives in the repositories: unknown graph/filter -> `NotFoundError` (`GRAPH_NOT_FOUND`, `FILTER_NOT_FOUND`), stale version -> `ConflictError('VERSION_CONFLICT')`, duplicate filter key -> `FILTER_KEY_EXISTS`. Integrity violations of graph data (bad edge, CHECK failures) deliberately surface as raw Prisma errors; services must validate first.

### Graph ingestion and CRUD (Task 3, implemented)

- Flow: `graph.router` -> `graphFileUpload` (Multer, memory) -> `validate()` -> `GraphController` -> `GraphService` -> `parseJsonBuffer` / `GraphFileSchema` / `normalizeGraph` -> repositories. The controller only decodes the uploaded bytes (`ingestion/upload-parser.ts`); the service validates and normalizes **before** opening a transaction, so bad uploads never take a lock.
- **Unknown fields are preserved at every level** (decision: "preserve unknown fields at all levels"): `graphs.extra`, `nodes.extra`, `edges.extra` (jsonb objects, CHECK-constrained), plus vulnerabilities and `metadata` kept whole. `parseGraphFile()` (`graph-file.schema.ts`) uses Zod only to VALIDATE (output discarded) and then reads the preserved data from the validated RAW json, because Zod's output silently drops a `__proto__` key. Do not switch back to using Zod's parsed output for extras.
- Edge entries: unknown fields are copied to each expanded edge (own copy); duplicate edges merge their extras (later wins). `GraphData` = `{extra, nodes, edges}`; `replaceData` replaces the graph-level extra too. API: graph detail has `extra` (nullable); an edge has `extra` only when non-null.
- **`__proto__` keys are refused** by `parseJsonBuffer` (400): Prisma's JSON serialization silently drops that key at any depth (verified: PostgreSQL stored `{"keep":1}`), so storing would lose data silently. All other awkward keys round-trip (tested). jsonb does not preserve object key order.
- Vulnerability fields are all optional/free-form on purpose: the sample file does not define which are required.
- `normalizeGraph` splits `to`, dedupes edges, creates placeholders (appended after defined nodes, in first-reference order), rejects duplicate names (`DUPLICATE_NODE_NAME`), enforces `MAX_NODES`/`MAX_EDGES` (413). `parseJsonBuffer` rejects NUL characters (PostgreSQL cannot store them).
- Responses: node JSON is `{name, kind, language, path, publicExposed, placeholder, vulnerabilities, metadata, extra}` (unknown upload fields stay nested under `extra`); edges are `{from, to}`. ETag is the quoted version (`"3"`); `If-Match` accepts `3`, `"3"`, `W/"3"`, `*`.
- New graphs get the built-in filters from `modules/filters/builtin-filters.ts` (rule-language JSON; the rule schema/compiler arrives in Task 4). They are inserted in the same transaction as the graph.
- Cache: `GraphService` depends on the `GraphCache` port (`invalidate(id)`), currently `noopGraphCache`; Task 4's `GraphStore` should implement it and be passed as `graphCache` to `createServices`/`wireApp`. Invalidation happens only after a committed `replace` or `delete` (not on rename or failures).
- Content is always validated regardless of declared file type/name (name/type only decides 415 vs parsing). Wiring: `createServices()` (used by the seed script too) and `wireApp()` live in `container.ts`; `buildPrismaPersistence(prisma)` builds the real repositories + unit of work. `npm run seed` loads `fixtures/train-ticket-be.json` (46 defined nodes + placeholder `assurance-service` = 47 nodes, 98 edges).
- Test helpers: `createDatabaseTestApp(prisma, opts)` is the real app on the test schema; `createTestApp()` uses stubs that throw if graph storage is touched; `tests/helpers/fakes.ts` has jest-mock repositories and a fake unit of work; `tests/helpers/api.ts` has `uploadGraph`/`replaceGraph` (`name: undefined` omits the field).

### Graph engine and rule language (Task 4, implemented)

- `src/graph-engine/` is plain TypeScript (a test, `tests/unit/architecture.test.ts`, fails if it imports anything outside the folder). Files: `graph-snapshot.ts` (immutable `GraphSnapshot`: `nodes` Map in file order, `outgoing` Map<node, Map<target, edge>> keeping the edge objects, `incoming` Map<node, Set>, `filterIndex` Map<key, Set>; built by `buildSnapshot(source, filters)`, which evaluates every predicate once and keeps placeholders out of the index), `conditions.ts` (`Condition` tree `filter | or | and | not` -> Set of names; `UnknownFilterError`), `traversal.ts` (`reachable`, iterative BFS), `route-finder.ts` (`findRoutes`), `graph-store.ts` (`GraphStore<S>`).
- **Route semantics** (agreed): walks, not simple paths; start/end nodes count as `through`; no roles = whole graph; unconstrained role = all nodes; a node alone is a route if it is both a start and an end. Algorithm: `F` = reachable from starts, `B` = reaches ends; with a through set `M`, `F1` = reachable from `M ∩ F`, `B1` = reaches `M ∩ B`; node on a route iff `(F1 ∧ B) ∨ (F ∧ B1)`, edge iff `(u∈F1 ∧ v∈B) ∨ (u∈F ∧ v∈B1)`. `tests/unit/graph-engine/route-finder.oracle.test.ts` checks this against an independent brute-force definition (`tests/helpers/route-oracle.ts`, product graph + Floyd-Warshall) on 4,000 random graphs; keep it passing when touching the finder.
- Result: `{ nodes: [{node, roles, filters}], edges }` where `roles` are the roles the node *really* plays (a start only if it can reach an end through M) and `filters` are the filters named in the query that it matches. Nodes come in file order (placeholders last), edges grouped by source node. Edge objects are returned as stored (so `extra` survives).
- `GraphStore<S>` implements the `GraphCache` port structurally (`invalidate(id)`): shared in-flight loads, `invalidate` marks an in-flight load stale (readers already waiting still get its result, but it is not cached and later readers start a fresh load), `null` and failures are not cached, LRU bound (`maxEntries`, default 50). Wired in Task 5 (see below).
- Rule language in `src/modules/filters/rules/`: `rule.types.ts` (types, `RULE_LIMITS`), `rule.schema.ts` (`validateRule`/`parseRule`: hand-dispatched validator that reports every issue with its path, Zod only for operator values; recursion is cut at the depth limit so hostile input cannot overflow the stack; throws 400 `INVALID_FILTER_RULE`), `field-resolver.ts` (own-property-only path lookup, so `metadata.constructor` cannot reach inherited members), `rule.compiler.ts` (`compileRule` -> predicate over `FilterableNode`; never throws). Semantics: missing = absent or null; `neq`/`notIn`/`notExists` are exact complements of `eq`/`in`/`exists`; numeric operators and `contains` are false for non-numbers/non-strings. `some` is only valid on `vulnerabilities`; inside `where` fields resolve against the vulnerability object. `BUILTIN_FILTERS` (Task 3) are valid rules in this language (tested).
- Test helpers: `tests/helpers/engine.ts` (`snap({nodes, placeholders, edges, filters})` builds a snapshot with filters by name), `tests/helpers/sample-engine.ts` (the sample file with the built-in filters compiled from their stored rules).

### Filters and routes API (Task 5, implemented)

- **One shared store.** `createServices()` (container.ts) builds exactly one `GraphStore<LoadedGraph>` with the loader from `modules/queries/graph-loader.ts` and one composite `GraphCache` (store + optional observer); `GraphService`, `FilterService` and `QueryService` all use it. `createContainer` builds services once and passes them to `wireApp(options, services)` — never call `createServices` twice for one app (two caches would go stale independently). `ServiceOptions.graphCache` is only an extra observer (tests use it to see invalidations).
- **`LoadedGraph`** = `{ snapshot, filters (records), unusable (Set of keys) }`. The loader reads `findWithData` + `filters.list`, runs `parseRule` + `compileRule` on every stored definition and `buildSnapshot`. A stored rule that no longer compiles (or has `definitionVersion` != `CURRENT_DEFINITION_VERSION`) is skipped, logged with `logger.warn`, and put in `unusable`: its `matchCount` is `null`, routes using it get `409 FILTER_UNAVAILABLE`, other filters keep working, `PUT` repairs it.
- **`FilterService`**: reads (`list`/`get`/`preview`) come from the store; writes validate the rule with `parseRule` *before* the transaction, then `unitOfWork.run`: `graphs.bumpVersion(id)` first, then the checks/writes (limit `MAX_FILTERS_PER_GRAPH` = 100 counted inside the locked transaction; built-in filters -> `BUILTIN_FILTER_READ_ONLY` 409), then `cache.invalidate` after commit and a re-read through the store for the response. `PUT` replaces the whole filter (omitted description -> null). Filter key pattern lives in `filter.types.ts` (`FILTER_KEY_PATTERN`) and must stay identical to the `graph_filters_key_format_check` CHECK.
- **`QueryService.routes`**: loads from the store (404 if missing), collects *all* unknown filters into one `UNKNOWN_FILTER` 400 (path = role), then `findRoutes`. `RouteQueryParamsSchema` is strict (a typo like `?strat=` is a 400). `toRouteQuery` joins repeated values of a role with `or`; AND across roles is the engine's semantics. Response nodes are the graph node DTO plus `matched: { roles, filters }`; edges carry `extra` only when present.
- **Routers**: filter and query routers are mounted at `/graphs` next to the graph router (paths `/:id/filters…`, `/:id/routes`); `GET /filters/:key` etc. do not clash with `POST /filters/preview`. `src/http/middleware/error-handler.ts` reports an unrecognized property at its own path.
- **Docs**: every controller route has a `registerXxxDocs`; `tests/integration/api/docs.test.ts` fails if the Express routers and `openapi.json` differ in either direction, so a new route must be documented in the same change.
- **Test helpers**: `tests/helpers/loaded.ts` (`storeFor(graph, filters)` = real loader + store over fake repositories), `tests/helpers/api.ts` (`smallGraphFile()`, `HIGH_SEVERITY_RULE`, path helpers), `tests/helpers/fakes.ts` (`filterRecord`, `silentTestLogger`).

## Gotchas

- **One `PrismaClient` per process** (`getPrismaClient(url)` / `disconnectPrisma()` in `src/infrastructure/prisma.ts`; throws if asked for a different URL). Only `src/container.ts` and `scripts/seed.ts` may call `getPrismaClient`; `createPrismaClient` builds an extra client and is for tests only. `tests/unit/architecture.test.ts` enforces this by scanning `src/` and `scripts/`.
- `GRAPH_CACHE_MAX_ENTRIES` (default 50, in `.env`, validated in `src/config/env.ts`) sets `GraphStore.maxEntries` via `createServices({ graphCacheMaxEntries })`; `createContainer` passes it. New env variables also need adding to the README table and block, and to the real `.env`.

- Jest uses `ts-jest` emitting CommonJS (see `jest.config.js`): Prisma 7's generated client uses dynamic `import()`, which Jest's VM rejects otherwise. Type checking is only via `npm run typecheck` (`isolatedModules` on).
- `tests/helpers/load-test-env.ts` copies `.env` values into `process.env` manually (`process.loadEnvFile` doesn't reach Jest's sandbox) and forces `NODE_ENV=test`, `LOG_LEVEL=silent`.
- Integration tests use the `test` schema of the same database: `tests/helpers/global-setup.ts` drops/recreates it and runs `prisma migrate deploy` once per run; tests call `createTestPrisma()` and `resetDatabase()` (TRUNCATE ... CASCADE). `globalSetup` runs outside the module mapper, so it must not import anything from `src/`. Jest runs with `maxWorkers: 1` because test files share that schema.
- `npx jest <path> --selectProjects integration`: put the path **before** `--selectProjects`, which swallows following arguments.
- CHECK constraint names (e.g. `nodes_kind_required_check`) are asserted by `tests/integration/db/constraints.test.ts`; rename them in the migration and the test together.
- Pinned on purpose: Prisma 7.10.1 (npm `latest` is an 8.0 RC) and TypeScript 6.0.3 (ts-jest doesn't support TS 7). npm 12 blocks install scripts by default; allowed ones are listed under `allowScripts` in `package.json`.
- Inside Docker the DB host is `postgres`; compose overrides `DATABASE_URL` while still reading the same `.env`. The sample graph is `fixtures/train-ticket-be.json` (the user's original file): 46 defined nodes + placeholder `assurance-service` = 47 nodes, 98 edges (asserted by tests).
